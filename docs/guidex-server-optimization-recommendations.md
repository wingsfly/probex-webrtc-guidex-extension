# GuideX 数字人交互 — 服务端优化建议清单

> 面向 iFlytek / GuideX 后端团队。所有结论均来自 ProbeX 探针在**迪拜 Chrome ↔ 利雅得服务端**的实测(2026-09-05,数千轮自动拨测 + 实时协议抓取)。
> 详细数据见同目录 [interaction-metrics-analysis.md](interaction-metrics-analysis.md) 与 [network-latency-analysis-riyadh.md](network-latency-analysis-riyadh.md)。

## 背景:一次交互的时间构成(avg,n=234)

端到端 `总交互 = 26.5s`,其中 **87% 是内容播放**(用户说话 3.3s + 回复播放 ~14~20s),**真正的开销/等待仅 ~12%(~3.3s)**。用户"干等"的核心是**说完→听见回复 = ~2.2s**,拆分:

| 子段 | avg | 占感知等待 | 归属 |
|------|----:|-----:|------|
| ASR 收尾(说完→最终识别) | 435ms | 20% | 服务端 |
| **LLM 生成回复** | **926ms** | **42%** | **服务端** |
| **TTS 合成+首块下发** | **839ms** | **38%** | **服务端** |

> 结论:感知等待的 **80% 来自 LLM + TTS,全部在服务端**;客户端侧已无优化空间。以下按 ROI 排序。

---

## P0 — 高优先级(收益大 / 可行性高)

### 1. 连接/会话复用(不要每轮新建 WSS)
- **现象**:每次交互都新建一条 `wss://.../voiceDictation/<uuid>` 连接(实测抓到 28 个不同 UUID)。
- **代价**:每轮一次全新 WSS 握手 = **~150ms(TCP+TLS+WS Upgrade,3 个网络 RTT)**,纯网络往返。
- **建议**:跨轮复用 voiceDictation 会话/长连接;或至少复用 TCP+TLS(HTTP/2 或 WS keep-alive)。
- **预期**:每轮省 ~150ms 建连;配合 TLS 会话恢复可近乎归零。

### 2. LLM 首响应加速(感知等待最大项,42%)
- **现象**:最终 ASR → 首个 TTS 事件 = **avg 926ms,最高 2883ms**;输入固定却有 ~800ms 抖动。
- **判断**:大模型生成 + 排队/负载波动。
- **建议**:首 token 流式触发 TTS(边生成边合成)、模型预热/常驻、降低排队。
- **预期**:感知等待中最大的一块;流式化后可显著前移"开口"时刻。

### 3. 流式 TTS(首块合成+下发,38%)
- **现象**:首个 TTS 事件 → 客户端真正听到音频 = **~839ms**。
- **建议**:TTS 边合成边下发首块,而非整句合成后再发;压缩首块合成延迟。
- **预期**:直接砍掉这 ~839ms 的大部分,用户更快听到回复。

---

## P1 — 中优先级(网络 / 协议)

### 4. 端点就近部署 / 修复选路
- **现象**:端点在**华为云利雅得**(AS136907);迪拜 du → 在 UAE-IX 交给 **STC(AS39386)** → 利雅得,实测 RTT **~50ms**。
- **对照**:同在利雅得的另一节点(经不同对等)RTT 仅 **~27ms**;理论直连 ~15ms。→ **50ms 是 du→STC 选路绕行,非物理距离**。
- **建议**:(a) 就近 UAE 部署/复制端点(RTT 可降到 <10ms);(b) 或推动华为云/STC 优化对 du/UAE-IX 的对等选路;(c) 近迪拜边缘终结 TLS/WSS、回源走优化骨干。
- **预期**:每个 RTT 50→~15ms,握手类开销(3 RTT)从 ~150ms 降到 ~45ms。

### 5. TLS 1.3 会话恢复 / 0-RTT
- **现象**:每轮全新 WSS 需完整 TLS 握手(端点已支持 TLS 1.3,单 RTT)。
- **建议**:开启会话恢复(session ticket)/ 0-RTT,复用时跳过完整握手。
- **预期**:配合第 1 项,重连握手接近 0-RTT。

### 6. ⚠️ 提供稳定、可靠的"回复结束"信号 + 协议版本化
- **现象**:协议改版后 **`tts_duration` 事件消失**,导致:(a) 我方无法统计 TTS 合成时长;(b) **失去唯一可靠的"回复完成"判据**,客户端只能退化为**固定 35s 超时**等待(无法提前结束,每轮白等)。ASR 协议也从 IAT 改为 `h5VoiceInput`(payload 嵌套 JSON),曾导致识别解析中断。
- **建议**:提供一个**明确、文档化、稳定**的"整段回复结束"标志(如 autoReport 上的 final 标记),并对协议做**版本化/变更通知**。
- **预期**:客户端可据此即时结束轮次(省下每轮 ~10~20s 的固定等待),且协议变更不再静默打断集成方。

---

## P2 — 低优先级(体验细节)

### 7. ASR 流式中间结果(可选)
- **现象**:ASR 实为**非流式**——音频播放期间基本无带词中间结果,整句在结束后一次性返回(status=1 紧接 status=2,相隔 ~2ms)。仅偶发一次早期 partial。
- **建议**:若产品需要更低的"首字"体感,可在音频流式期间下发增量识别结果。

### 8. ASR 收尾延迟(~435ms)
- **现象**:发出"说完"(status=2)后 ~330ms(+网络)返回最终结果。属正常,但仍是感知等待的一部分。
- **建议**:如有空间,压缩最终解码/标点/rescoring 的收尾时间。

---

## 附:已确认良好、无需改动
- **音画同步健康**:数字人口型稳定**领先声音 ~60~92ms**(方向自然、无声音抢跑);结尾音频比口型长 ~185ms(占 13s 的 1.4%)。
- 客户端侧测量准确;上述所有延迟项均为服务端可控。

| 优先级 | 项目 | 每轮预期收益 |
|:--:|------|------|
| P0 | 连接/会话复用 | ~150ms |
| P0 | LLM 首响应流式 | 感知等待最大项(~926ms 中的大部分) |
| P0 | 流式 TTS 首块 | ~839ms 中的大部分 |
| P1 | 端点就近/修选路 | RTT 50→~15ms(握手类 ~150→~45ms) |
| P1 | TLS 会话恢复/0-RTT | 重连握手趋零 |
| P1 | 稳定"回复结束"信号 + 协议版本化 | 客户端省固定等待 + 集成稳定性 |
| P2 | ASR 流式中间结果 / 收尾提速 | 首字体感 / ~百 ms |
